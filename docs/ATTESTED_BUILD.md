# Approved v0.1.0 build safeguards

Release immutability was enabled via the owner-authenticated API and read back as `enabled:true, enforced_by_owner:false`. This protects future immutable releases; no tag or release was created. If an administrator must configure it manually: repository Settings → General → Releases → Enable release immutability. Verify with `gh api repos/doksanbes/agentbridge/immutable-releases` before publication.

## Workflow boundary

`attested-build.yml` is manual-only, restricted to this repository's main ref. It accepts no arbitrary ref/digest inputs. It checks out approved source `1aa6cd22ae92dfba99df50f898234f460ccf96d3` and requires archive SHA-256 `b519cbe31517715d6b1b82999a0fb64fa0adca42d95f4dcf57c3fdfcc7eeb8c4`. A mismatch or dirty source aborts before attestation. The source audit, full tests and isolated package installation run against that exact checkout. No build cache is restored.

Official checkout/setup-node/attest actions are pinned by SHA. Only the manual job has contents:read, id-token:write and attestations:write. There is no contents:write, packages:write, artifact-metadata:write, release creation, registry push or artifact upload step. Storage records are disabled. Only attestation statements are uploaded to GitHub's attestation API by the official action. Archives remain ephemeral on the runner; rebuild locally and verify against the digest when needed. The approved source and locked compiler dependencies are trusted code within this job; the token scope applies to the whole job, not only the action. No unreviewed PR code may run with these permissions.

## Source identity is distinct from signer identity

The new workflow necessarily lives in a later commit than the approved source. Its default SLSA provenance identifies the workflow invocation source; checking out an older commit does not make GitHub's OIDC source identity that older commit. Therefore the workflow emits two attestations for the same archive:

1. Standard SLSA provenance, generated by official `actions/attest`.
2. A custom signed `https://github.com/doksanbes/agentbridge/attestations/approved-source/v1` predicate explicitly recording the independently checked repository, approved commit and digest.

Neither predicate alone is a certificate of safe code. Verify the signer workflow **and its reviewed workflow commit SHA**, then enforce the custom predicate fields. A compromised trusted workflow could lie in a custom predicate. Source code review, pinned identity, deterministic reproduction and the owner-controlled main branch are essential trust assumptions. A raw JSON statement or local manifest is not signature verification.

## Verification procedure

After separate merge authorization and an approved manual dispatch from main, the workflow itself verifies both signatures with `gh attestation verify`, pinned to repository, workflow path and `$GITHUB_SHA`, then runs the semantic policy on successful verifier JSON. It fails if source identity or subject digest differs. A successful generation without a successful verification step does not close the blocker.

For local verification, use a rebuilt exact archive and the **reviewed orchestration commit**, not the approved source SHA, as `<workflow-sha>`:

```sh
gh attestation verify agentbridge-0.1.0.tgz --repo doksanbes/agentbridge --signer-workflow doksanbes/agentbridge/.github/workflows/attested-build.yml --signer-digest <workflow-sha> --predicate-type https://slsa.dev/provenance/v1
gh attestation verify agentbridge-0.1.0.tgz --repo doksanbes/agentbridge --signer-workflow doksanbes/agentbridge/.github/workflows/attested-build.yml --signer-digest <workflow-sha> --predicate-type https://github.com/doksanbes/agentbridge/attestations/approved-source/v1 --format json > verified-source.json
node scripts/attestation-policy.mjs verify verified-source.json
```

Run the policy only after the preceding command exits successfully. Review the script from the orchestration commit. No attestation is claimed by these instructions or unit tests. The workflow cannot be exercised on a PR ref because its main-only guard intentionally prevents that. It must be merged separately before a main dispatch can generate/verify real attestations.

The first checksum names the archive digest above; manifest sidecar varies by recorded build toolchain and must be reviewed/hashed separately.
